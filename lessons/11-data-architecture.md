# Урок 11. Архітектура, SwiftData та асинхронні дані

## Мета

З'єднати інтерфейс із моделлю та постійним сховищем, не перетворюючи SwiftUI View на місце для всієї логіки. Наприкінці уроку ти зможеш зберігати локальні записи, завантажувати дані з мережі та показувати користувачеві зрозумілий стан програми.

## Що ти вивчиш і навіщо

- **Архітектуру** — як розкласти програму на частини, щоб її було легше читати, тестувати й змінювати.
- **SwiftData** — як зберігати об'єкти на диску, щоб вони не зникали після закриття програми.
- **Асинхронність** — як чекати на відповідь мережі, не «заморожуючи» інтерфейс.
- **Стани UI** — як відрізнити завантаження, успіх, порожній список і помилку.

Корисне правило: View має описувати, **що показати**, а не містити всі правила бізнесу, SQL-подібні запити та мережеві деталі.

## Як розділити відповідальність

Уяви трекер навчання:

1. **Модель** описує дані: назву теми, статус виконання, дату створення.
2. **Бізнес-правила** вирішують, що означає «виконано» або чи можна перейти до наступного кроку.
3. **Сховище** читає та записує дані. У цьому уроці локальним сховищем буде SwiftData.
4. **Сервіс мережі** отримує дані з HTTP API та перетворює JSON на Swift-типи.
5. **View** показує стан і реагує на натискання кнопок.

Таке розділення не вимагає складного фреймворку. Навіть кілька невеликих типів кращі за один великий `View`, у якому змішані кнопки, мережеві запити й правила програми.

### Терміни простими словами

- **Джерело істини** — місце, якому програма довіряє як актуальному стану. Для локального трекера це може бути SwiftData, а View лише відображає його.
- **Стан** — те, що може змінюватися під час роботи: `isLoading`, список записів або повідомлення про помилку.
- **Контекст моделі** — робочий об'єкт SwiftData, через який вставляють, змінюють і видаляють моделі.
- **Асинхронна операція** — робота, яка може завершитися пізніше, наприклад мережевий запит. `await` означає «почекати результат, не блокуючи інтерфейс».

## SwiftData: модель і життєвий цикл запису

Почнімо з моделі. Макрос `@Model` повідомляє SwiftData, що об'єкти цього типу можна зберігати. `import SwiftData` потрібен саме для цього макросу.

```swift
import SwiftData

@Model
final class StudyItem {
    var title: String
    var isDone: Bool

    init(title: String, isDone: Bool = false) {
        self.title = title
        self.isDone = isDone
    }
}
```

У SwiftUI застосунок зазвичай отримує контейнер моделі на верхньому рівні, а View — контекст і запит:

```swift
import SwiftData
import SwiftUI

@main
struct StudyApp: App {
    var body: some Scene {
        WindowGroup {
            StudyListView()
        }
        .modelContainer(for: StudyItem.self)
    }
}

struct StudyListView: View {
    @Environment(\.modelContext) private var modelContext
    @Query private var items: [StudyItem]

    var body: some View {
        List(items) { item in
            Text(item.title)
        }
        .toolbar {
            Button("Додати") {
                modelContext.insert(StudyItem(title: "Нова тема"))
            }
        }
    }
}
```

Що відбувається крок за кроком:

1. `.modelContainer(for:)` створює та під'єднує сховище для `StudyItem`. Це аналог «підготувати базу даних».
2. `@Environment(\.modelContext)` дістає контекст, який SwiftUI передав цьому екрану.
3. `@Query` читає записи зі сховища й оновлює View, коли дані змінюються.
4. `insert` додає новий об'єкт у контекст. SwiftData зберігає зміни контейнера без ручного написання SQL.
5. Закриття й повторний запуск застосунку — важлива перевірка: запис має залишитися.

Для редагування зміни властивість моделі, наприклад `item.isDone.toggle()`. Для видалення у списку можна використати `onDelete` і `modelContext.delete(item)`. Не змішуй ці дії з правилами на кшталт «не можна завершити тему без назви» — такі правила краще винести в окремий тип або метод.

> У Xcode кнопка **Run** (трикутник ▶) збирає застосунок і запускає його в обраному симуляторі. У верхній панелі поруч із нею обирають схему застосунку та пристрій. Якщо ти змінив модель або контейнер і отримав дивну стару поведінку, спочатку зупини застосунок кнопкою **Stop** (квадрат ■), а потім перевір дані симулятора; не видаляй дані без потреби.

## Асинхронні дані з мережі

Локальні записи мають працювати навіть без інтернету. Мережеві дані краще розглядати як додаткове джерело, яке може бути повільним або недоступним.

`URLSession` виконує HTTP-запит, `Codable` декодує JSON у Swift-тип, а `async/await` робить послідовність кроків читабельною. Приклад сервісу без секретного ключа:

```swift
import Foundation

struct DemoPost: Decodable {
    let id: Int
    let title: String
}

enum APIError: Error {
    case badResponse
}

func loadPosts() async throws -> [DemoPost] {
    let url = URL(string: "https://jsonplaceholder.typicode.com/posts")!
    let (data, response) = try await URLSession.shared.data(from: url)

    guard let httpResponse = response as? HTTPURLResponse,
          (200..<300).contains(httpResponse.statusCode) else {
        throw APIError.badResponse
    }

    return try JSONDecoder().decode([DemoPost].self, from: data)
}
```

Розбір:

- `async` позначає функцію, яка може чекати.
- `throws` попереджає, що результатом може бути помилка.
- `try await` чекає завершення запиту та передає помилку далі, якщо вона сталася.
- Перевірка статус-коду потрібна, бо HTTP-відповідь може прийти навіть із кодом помилки.
- `JSONDecoder` не виправляє неправильний JSON: якщо форма відповіді не збігається з `DemoPost`, декодування завершиться помилкою.

У View запускай таку роботу в `task`, а не в `body`:

```swift
struct RemotePostsView: View {
    @State private var posts: [DemoPost] = []
    @State private var message: String?
    @State private var isLoading = false

    var body: some View {
        Group {
            if isLoading {
                ProgressView("Завантаження…")
            } else if let message {
                Text(message)
            } else if posts.isEmpty {
                ContentUnavailableView("Немає даних", systemImage: "tray")
            } else {
                List(posts, id: \.id) { post in
                    Text(post.title)
                }
            }
        }
        .task {
            isLoading = true
            defer { isLoading = false }
            do {
                posts = try await loadPosts()
            } catch is CancellationError {
                // Скасування під час виходу з екрана — не помилка для користувача.
            } catch {
                message = "Не вдалося завантажити дані. Перевір з'єднання."
            }
        }
    }
}
```

`.task` прив'язує асинхронну роботу до життєвого циклу View: коли екран зникає, SwiftUI може скасувати задачу. Це не гарантує, що кожна стороння операція миттєво припиниться, але код має коректно ставитися до `CancellationError` і не показувати скасування як поломку.

## Як думати над задачею

Перед кодом запиши відповіді на чотири питання:

1. Які дані мають пережити перезапуск? Їх зберігай у SwiftData.
2. Які дані можна отримати повторно? Їх можна завантажувати мережею.
3. Що побачить людина, поки чекає? Додай loading-стан.
4. Що станеться без мережі або без записів? Передбач error та empty-стани.

Після цього намалюй простий потік: **натиснув “Оновити” → loading → success / empty / error**. Якщо цей потік зрозумілий на папері, його легше реалізувати у View.

## Практичне завдання

1. Перенеси модель `StudyItem` із кросплатформного проєкту в Apple App target або окремий спільний модуль.
2. Під'єднай SwiftData й перевір, що записи переживають перезапуск. Для перевірки додай запис, натисни **Stop**, потім знову **Run**.
3. Додай асинхронне завантаження демонстраційних даних із відкритого API.
4. Покажи loading, success, empty та error стани. Для empty-стану перевір порожній масив, а не лише `nil`.
5. Додай кнопку повторної спроби після помилки й переконайся, що повторний запит не створює дублікати локальних записів.
6. Переконайся, що відсутність мережі не ламає локальний трекер: вимкни мережу симулятора або використай некоректну адресу й відкрий локальний список.

Не додавай приватні ключі або секрети до репозиторію. Не роби мережевий запит без обробки помилки та скасування.

## Типові помилки

- **Запит у `body`.** `body` може обчислюватися багато разів, тому запит повторюватиметься. Запускай його через `.task` або окрему дію кнопки.
- **Немає перевірки HTTP-статусу.** `URLSession` не вважає код 404 або 500 помилкою сам по собі. Перевіряй `HTTPURLResponse` і діапазон 200–299.
- **Помилка показується як порожній список.** Користувач не знає, чи даних справді немає, чи мережа недоступна. Розділяй `error` та `empty`.
- **SwiftUI View зберігає всю логіку.** Великий `body` важко тестувати. Винеси правила, модель і мережевий сервіс в окремі типи.
- **Примусове розгортання URL або відповіді без перевірки.** `!` може завершити застосунок. Для реальної адреси використовуй перевірку й покажи зрозумілу помилку.
- **Ігнорування скасування.** Після виходу з екрана результат старого запиту може змінити неактуальний стан. Обробляй `CancellationError` і не показуй його як помилку мережі.
- **Дублікат джерел істини.** Якщо одні записи живуть у `@State`, а інші — у SwiftData, вони можуть розійтися. Визнач, яке сховище є основним, і синхронізуй дані свідомо.

## Перевір себе

Відповідай без підглядання в код:

1. Для чого потрібні модель, сховище та View, і чому не варто змішувати їх?
2. Що роблять `@Model`, `ModelContainer`, `modelContext` і `@Query`?
3. Чим відрізняються loading, empty, success та error?
4. Чому `async/await` не блокує інтерфейс?
5. Навіщо перевіряти HTTP-статус, якщо `URLSession` повернув `data`?
6. Що має відбутися, коли View зникає під час мережевого запиту?

Ти готовий перейти далі, якщо можеш пояснити шлях даних від натискання кнопки до View, відновити запис після перезапуску, показати чотири стани завантаження та пояснити, чому застосунок залишається корисним без мережі.

## Критерії готовності

- [ ] Бізнес-правила не залежать від SwiftUI View.
- [ ] Записи зберігаються після закриття й повторного запуску.
- [ ] Є зрозумілий стан помилки та порожнього списку.
- [ ] Асинхронна операція не блокує інтерфейс.
- [ ] Можу пояснити, де знаходиться джерело істини для даних.
