## Мета

Завершити першу частину курсу: створити кросплатформний консольний Study Tracker, логіка та модель якого стануть основою майбутнього macOS-застосунку на SwiftUI.

Це не просто ще одна вправа з меню. Ти збереш маленький, але повний застосунок: він прийматиме дані, перевірятиме їх, виконуватиме правила, зберігатиме результат у JSON і матиме автоматичні тести. На Mac ти не починатимеш Swift з нуля — перенесеш уже перевірену логіку в графічний інтерфейс.

## Що ти вивчиш і навіщо

Після уроку ти зможеш:

- розділяти **модель** (які дані існують), **бізнес-логіку** (що з ними дозволено робити), **сховище** (як дані записуються на диск) і **CLI** (як користувач взаємодіє з програмою);
- створити типи, які можна кодувати в JSON, і відновлювати їх після наступного запуску;
- обробляти очікувані помилки без аварійного завершення програми;
- запускати `swift build`, `swift test` і `swift run` та читати результат цих команд;
- підготувати код до майбутнього SwiftUI-інтерфейсу на macOS.

Головна ідея: інтерфейс може змінюватися, але правила Study Tracker мають залишатися однаковими. Консольне меню — лише один спосіб викликати ці правила; згодом ним стане вікно macOS.

## Як думати над задачею

Перед написанням коду розклади задачу на питання:

1. **Що зберігаємо?** Один навчальний пункт має ID, назву, статус і дату створення.
2. **Що дозволено?** Можна додати пункт, змінити його статус, знайти за ID і відфільтрувати список.
3. **Що може піти не так?** Назва порожня або некоректна, ID не знайдено, файл відсутній чи містить пошкоджений JSON.
4. **Де має жити кожне правило?** Перевірка назви — у моделі або сервісі, робота з файлами — у сховищі, читання команд — у CLI.
5. **Як це перевірити без ручного запуску?** Для кожного правила потрібен тест: звичайний випадок, помилка і крайовий випадок.

Не починай із меню. Якщо спочатку зробити `print` і `readLine()`, правила швидко змішаються з введенням і їх буде важко тестувати.

## Модель: найменший корисний приклад

Модель описує дані, а не спосіб їх показу. Ось короткий компільований приклад для Swift Package або іншого консольного проєкту з `Foundation`:

```swift
import Foundation

enum StudyStatus: String, Codable {
    case planned
    case inProgress
    case completed
}

struct StudyItem: Identifiable, Codable {
    let id: UUID
    var title: String
    var status: StudyStatus
    let createdAt: Date
}

let item = StudyItem(
    id: UUID(),
    title: "Повторити enum",
    status: .planned,
    createdAt: Date()
)

print(item.title)
```

Тут `enum` обмежує статуси трьома дозволеними значеннями. `String` дає їм текстове представлення, а `Codable` дозволяє перетворювати значення в JSON і назад. `struct` підходить для одного запису даних. `Identifiable` означає, що в об’єкта є `id`; пізніше SwiftUI зможе використовувати його для списків. `let` забороняє випадково змінити ID і дату створення, а `var` дозволяє змінювати назву або статус.

Назва не повинна бути лише пробілами. Перевіряй очищене значення до створення або збереження запису:

```swift
func validatedTitle(_ input: String) -> String? {
    let title = input.trimmingCharacters(in: .whitespacesAndNewlines)
    return title.isEmpty ? nil : title
}
```

`trimmingCharacters(in:)` прибирає пробіли на краях. Повернення `nil` чітко повідомляє викликачу, що назву треба відхилити або попросити ще раз.

## Покроковий розбір архітектури

1. **Модель.** Описує `StudyItem` і `StudyStatus`. Вона не повинна читати `readLine()` або друкувати меню.
2. **Сервіс або менеджер.** Зберігає масив пунктів і реалізує `add`, зміну статусу, пошук та фільтрацію. Саме тут перевіряються правила та повертаються зрозумілі помилки.
3. **Сховище.** Отримує URL файла, читає байти через `Data(contentsOf:)`, декодує `JSONDecoder`, а для запису використовує `JSONEncoder` і `write(to:)`. `FileManager` допомагає перевірити, чи існує файл і створити потрібний каталог.
4. **CLI.** Показує варіанти, читає текст користувача, перетворює його на виклик сервісу та показує результат. CLI не має самостійно змінювати масив або розбирати JSON.
5. **Тести.** Викликають модель, сервіс і сховище напряму. Завдяки цьому тестам не потрібні клавіатура чи ручне натискання пунктів меню.

Під час декодування передбач щонайменше три ситуації: файл ще не існує — почни з порожнього списку; JSON пошкоджений — поверни помилку, не втрачаючи старі дані; запис із потрібним ID відсутній — повідом про це користувачу.

## Кросплатформність

Основний код не повинен залежати від Apple SDK або SwiftUI. Перевіряй його на своїй ОС; якщо заявляєш підтримку іншої ОС, спочатку реально запусти там build і tests.

Тримай платформний код на межі програми. `Foundation` потрібен для `UUID`, `Date`, JSON і файлової системи, але модель та правила не повинні імпортувати SwiftUI. Так їх буде легше перенести в macOS-проєкт.

## Перехід до MacBook: macOS, Xcode і SwiftUI

Цей Issue завершує кросплатформну частину. Після отримання MacBook продовжуй з [Issue #9 — macOS та Xcode](https://github.com/juv4uk/swift-learning/issues/9), а не починай Swift з нуля.

На Mac тобі знадобляться такі поняття:

- **macOS** — операційна система Mac. Вона надає вікна, меню, файлову систему та інструменти розробника.
- **Xcode** — програма Apple для створення, запуску й тестування застосунків. У ній є редактор коду, навігатор файлів, кнопки запуску та панель помилок.
- **Проєкт або workspace** — контейнер із файлами, налаштуваннями та тестами. Навігатор зліва потрібен, щоб відкривати ці файли.
- **Target** — конкретний продукт, який Xcode збирає, наприклад macOS-застосунок або набір тестів.
- **Scheme** — вибір того, що запускати, і з якими налаштуваннями. На початку обери схему свого застосунку.
- **Run (▶)** — збирає проєкт і запускає його. Якщо є помилка компіляції, Xcode покаже її в редакторі та Issue navigator.
- **Stop (■)** — зупиняє запущену програму.
- **Build** — лише перевіряє, чи можна зібрати код; **Test** запускає автоматичні тести. Їх не слід плутати: успішна збірка ще не доводить, що правила працюють правильно.

**SwiftUI** — фреймворк для опису інтерфейсу декларативним кодом: ти описуєш, що має бути на екрані, а система оновлює його, коли змінюються дані. `List` може показувати StudyItem, `TextField` — приймати назву, `Button` — викликати дію, а `Picker` — вибирати статус. Спочатку перенеси модель і сервіс без змін, потім підключай ці елементи до екрана. Не дублюй правила в кнопці SwiftUI.

Коли створюєш macOS App в Xcode, зверни увагу на шаблон, назву продукту та мову SwiftUI. Кнопка запуску використовує вибрану схему, а список доступних запусків показує пристрої або Mac, на яких можна відкрити програму. Для першого кроку достатньо запуску на цьому Mac. Після створення проєкту додай або підключи спільний код, а тести запускай окремо через меню Product → Test.

## Типові помилки

- **Порожня назва проходить перевірку.** Причина: перевіряється лише `input.isEmpty`, тому рядок із пробілами вважається непорожнім. Виправлення: спочатку обрізати пробіли й перевірити очищений рядок.
- **ID створюється заново під час кожного завантаження.** Причина: ID не зберігається в JSON або запис замінюється новим. Виправлення: створювати `UUID()` лише для нового пункту і декодувати його зі збережених даних.
- **CLI змінює масив напряму.** Причина: найкоротше рішення здається зручним. Виправлення: усі зміни пропускати через сервіс, щоб їх можна було протестувати без меню.
- **Відсутній файл вважається пошкодженим.** Причина: будь-яка помилка читання обробляється однаково. Виправлення: відсутній файл трактувати як перший запуск, а помилку декодування показувати окремо.
- **Тест залежить від справжнього файла.** Причина: у тесті використано постійний шлях. Виправлення: передавати сховищу тимчасовий URL і очищати його після тесту.
- **Увесь код поміщено у SwiftUI View.** Причина: інтерфейс видно одразу, тому логіку легко додати туди ж. Виправлення: залишити модель, сервіс і сховище окремими та лише викликати їх із View.
- **Натиснуто Run, але не перевірено Test.** Причина: програма відкрилася, отже здається справною. Виправлення: запускати `swift test` або Product → Test і перевіряти помилкові та крайові сценарії.
