# Урок 12. Якість, налагодження та збірка

## Мета

Навчитися перевіряти застосунок, знаходити помилки й готувати повторювану збірку для локального тестування. Наприкінці уроку ти не лише запустиш Study Tracker, а й зможеш пояснити, чому вважаєш його готовим до демонстрації.

## Що ти вивчиш і навіщо

Якість — це не тільки відсутність помилок. Важливо, щоб застосунок:

- робив те, що обіцяє;
- не ламався після змін;
- був зручним для різних людей;
- збирався однаково на іншому комп’ютері;
- мав зрозумілу історію змін.

У цьому уроці ти познайомишся з тестами, налагодженням, доступністю, Git і різницею між режимами та етапами збірки. Не потрібно одразу знати всі можливості Xcode. Твоя мета — освоїти базовий повторюваний процес: змінити код → перевірити → знайти проблему → виправити → знову перевірити.

## Терміни простими словами

- **Unit-тест** — маленька автоматична перевірка однієї частини логіки, наприклад правила валідації назви.
- **Breakpoint** — позначка в коді, на якій виконання тимчасово зупиниться, щоб можна було подивитися значення змінних.
- **Debug** — пошук і виправлення причин неправильного результату.
- **Build (збірка)** — перетворення коду та ресурсів на застосунок, який можна запустити.
- **Configuration** — набір налаштувань збірки. Найчастіше використовують **Debug** для розробки та **Release** для підготовленішої збірки.
- **Signing** — підтвердження, хто створив застосунок і на яких пристроях або для яких можливостей його можна запускати.
- **Accessibility (доступність)** — спосіб зробити інтерфейс придатним для людей із різними потребами, зокрема для користувачів VoiceOver або клавіатури.

## 1. Тести поведінки в Xcode

Відкрий проєкт у Xcode. **Test Navigator** — це вкладка з іконкою, схожою на галочку, у лівій бічній панелі. Вона показує тестові файли та окремі тести. Кнопка запуску біля тесту запускає лише його, а кнопка запуску біля набору тестів — усі тести цього набору.

Пиши тести для поведінки, яку бачить користувач. Наприклад, перевіряй, що після додавання запис справді з’явився, а не те, що всередині використовується конкретний масив.

Ось короткий самодостатній приклад Swift-коду. Функція повертає `true`, якщо назва не порожня після вилучення пробілів:

```swift
import Foundation

func isValidTitle(_ title: String) -> Bool {
    !title.trimmingCharacters(in: .whitespacesAndNewlines).isEmpty
}

let title = "  Swift  "
print(isValidTitle(title)) // true
```

У тестовому target аналогічну поведінку можна перевірити так:

```swift
import XCTest

final class TitleValidationTests: XCTestCase {
    func testWhitespaceOnlyTitleIsInvalid() {
        XCTAssertFalse(isValidTitle("   "))
    }

    func testTitleWithLettersIsValid() {
        XCTAssertTrue(isValidTitle("  Swift  "))
    }
}
```

У цьому прикладі `XCTAssertFalse` очікує `false`, а `XCTAssertTrue` — `true`. Назва тесту пояснює сценарій, тому за повідомленням про помилку легше зрозуміти, що саме зламалося.

### Як розібрати тест покроково

1. `import XCTest` підключає інструменти тестування.
2. `TitleValidationTests` групує перевірки однієї поведінки.
3. Кожен метод, що починається з `test`, є окремим тестом.
4. Тест готує вхідне значення — рядок із пробілами або з текстом.
5. `XCTAssert...` порівнює фактичний результат із очікуваним.
6. Якщо перевірка не проходить, Xcode показує тест як невдалий і вказує місце проблеми.

Перед запуском переконайся, що `isValidTitle` доступна тестовому target. Якщо Xcode не бачить функцію, перевір, чи файл із нею додано до правильного target у File Inspector. Не копіюй функцію в тест лише для того, щоб тест «пройшов»: тоді ти перевірятимеш копію, а не код застосунку.

## 2. Як думати над задачею та знаходити помилку

Коли тест або дія в інтерфейсі не працює, не вгадуй виправлення навмання. Рухайся від факту до причини:

1. **Опиши очікування.** Наприклад: «після натискання Save назва з пробілів не має додаватися».
2. **Отримай стабільний сценарій.** Запиши точні кроки, які відтворюють проблему.
3. **Знайди межу.** Перевір, чи правильне значення приходить у функцію та чи правильне значення з неї виходить.
4. **Зупини виконання.** Постав breakpoint на рядок, де приймається важливе рішення.
5. **Перевір припущення.** Подивися на змінні, а не покладайся на здогад.
6. **Зроби найменшу зміну.** Після виправлення одразу повтори той самий сценарій і запусти тести.

### Breakpoints, variables, console і call stack

Breakpoint додається клацанням по полю з номерами рядків зліва від коду. Коли виконання доходить до нього, Xcode призупиняє програму. У нижній області налагодження можна побачити локальні змінні та їхні значення. **Console** показує повідомлення програми; її можна використати для тимчасового `print`, але не варто залишати випадкові діагностичні повідомлення у фінальному коді.

**Call stack** — це ланцюжок викликів: він показує, яка функція викликала поточну, а та — попередню. Це допомагає зрозуміти шлях виконання. Кнопка продовження запускає програму до наступного breakpoint, а кнопка покрокового виконання переходить до наступного рядка. Якщо breakpoint більше не потрібен, натисни його ще раз або прибери через список breakpoint.

Базовий LLDB можна використовувати для перегляду значення у консолі, наприклад командою `po title`, якщо в поточному місці існує змінна `title`. Команда працює лише для доступних у цьому контексті значень.

## 3. Доступність: перевірка очима та руками

Доступність — це частина якості, а не додаткова прикраса. Для кожного основного сценарію Study Tracker перевір:

- чи можна перейти між елементами клавіатурою без миші;
- чи зрозуміла назва кнопки та її дія;
- чи читає VoiceOver заголовок, поле та кнопку в логічному порядку;
- чи не обрізається текст при збільшенні розміру шрифту;
- чи достатній контраст тексту та фону.

У SwiftUI текст кнопки має описувати дію: `Button("Додати запис")` зрозуміліший за кнопку без підпису. Не ховай важливі пояснення лише в кольорі: помилку валідації треба передавати текстом або іншим зрозумілим способом. Якщо елемент має лише іконку, перевір його доступне ім’я через налаштування доступності та VoiceOver.

VoiceOver — вбудований засіб macOS та Apple-платформ, який озвучує вибраний елемент. Увімкнення та вимкнення VoiceOver залежить від налаштувань системи, тому під час перевірки користуйся системною довідкою, а не запам’ятовуй випадкову комбінацію клавіш. Важливо саме пройти сценарій: відкрити форму, перейти до поля, ввести значення, побачити повідомлення про помилку та зберегти запис.

## 4. Git і повторювана збірка

Перед фіксацією змін переглянь **diff** — список рядків, які додалися, змінилися або видалилися. Чистий diff не містить випадкових файлів, особистих налаштувань чи великих згенерованих каталогів. Коміт має коротко пояснювати одну логічну зміну, наприклад «Додати тести валідації запису».

README має відповісти іншій людині на три питання:

1. Що це за застосунок?
2. Як відкрити, зібрати та запустити його локально?
3. Які сценарії вже перевірені та які обмеження залишилися?

Додай скриншоти основних екранів і короткий опис архітектури. Не додавай секрети, ключі чи особисті шляхи до файлів. Після змін зроби чисту збірку через звичайну команду **Product → Clean Build Folder** у Xcode, а потім знову запусти тести та застосунок. Ця дія прибирає проміжні результати збірки; вона не виправляє помилки сама по собі, але допомагає відрізнити проблему коду від застарілого артефакту.

## 5. Debug, Release, Run, Archive та Export

- **Run** збирає та запускає застосунок у вибраному середовищі для швидкої розробки й перевірки.
- **Debug configuration** зручна під час розробки: у ній доступні засоби налагодження, а швидкість і розмір не є головною метою.
- **Release configuration** призначена для підготовленішої збірки. Вона може мати інші налаштування оптимізації, тому важливо перевіряти застосунок не лише в Debug.
- **Archive** створює збережений пакет збірки в Organizer. Це не те саме, що просто натиснути Run.
- **Export** бере архів і готує з нього варіант для конкретного способу розповсюдження. Експорт не означає, що застосунок уже опубліковано.

Для навчального завдання достатньо дослідити ці етапи та записати, що робить кожен із них. Не публікуй застосунок без окремого рішення.

### Signing basics

**Bundle identifier** — унікальне ім’я застосунку в системі. **Team** визначає обліковий запис розробника, який підписує збірку. **Provisioning** пов’язує застосунок, команду та дозволені умови запуску. **Capabilities** вмикають спеціальні можливості, але кожна зайва capability збільшує кількість налаштувань, які треба перевірити.

Якщо Xcode показує помилку signing, прочитай точний текст повідомлення. Спершу перевір вибрану Team, bundle identifier і налаштування target. Не вимикай захисні перевірки навмання й не додавай capability «про всяк випадок». Для локального навчального запуску не потрібно готувати публікацію.

## Практичне завдання: підготувати Study Tracker до демонстрації

Виконуй кроки по порядку й записуй результат у README:

1. Додай тести на додавання, редагування, видалення та валідацію. Для кожного тесту опиши вхідні дані, очікування і фактичний результат.
2. Відтворюй одну помилку навмисно й знайди її через breakpoint. Наприклад, передай порожню назву та перевір, де вона проходить без перевірки.
3. Перевір основні сценарії клавіатурою та VoiceOver: запуск, створення, редагування, видалення і повідомлення про помилку.
4. Перевір, що назви елементів доступні, а текст не обрізається при збільшеному розмірі.
5. Зроби чисту збірку, запусти тести ще раз і зафіксуй у README кроки локального запуску.
6. Переглянь Git diff, прибери випадкові файли, зроби зрозумілий коміт і додай скриншоти.
7. Досліди Archive/Export та signing, не публікуючи застосунок без окремого рішення.

## Типові помилки

| Помилка | Чому це проблема | Як виправити |
|---|---|---|
| Тест перевіряє приватну змінну замість поведінки | Такий тест ламається після безпечної зміни реалізації | Перевір результат, який бачить користувач або інший публічний компонент |
| Breakpoint поставлено після проблемного рядка | Виконання вже пройшло місце, де виникло неправильне значення | Постав breakpoint перед перевіркою або присвоєнням і подивися значення на вході |
| `print` залишився всюди в коді | Консоль стає шумною, а випадкові дані можуть потрапити в лог | Залиш лише корисні повідомлення або прибери тимчасову діагностику |
| Кнопка має тільки незрозумілу іконку | Користувач клавіатури або VoiceOver не знає її призначення | Додай зрозуміле доступне ім’я та перевір дію без миші |
| Перевірено лише Debug | Проблема може проявитися в іншій конфігурації | Окремо перевір Release-сценарій, коли це доречно для проєкту |
| У README немає точних кроків запуску | Інша людина не може повторити результат | Запиши порядок відкриття, вибір схеми, запуск і відомі обмеження |
| Archive сприймають як публікацію | Архів — це збережена збірка, а не автоматичне розміщення в магазині | Розділяй Run, Archive та Export і не виконуй публікацію без рішення |

## Перевір себе

Відповідай без підглядання, а потім перевір себе в Xcode:

1. Чим unit-тест відрізняється від ручної перевірки інтерфейсу?
2. Що показує breakpoint і для чого потрібен call stack?
3. Які три кроки ти зробиш, якщо тест раптом перестав проходити?
4. Чому доступність треба перевіряти клавіатурою та VoiceOver, а не лише візуально?
5. Чим відрізняються Debug і Release?
6. Чому Run, Archive та Export — різні дії?
7. Які дані про запуск має містити README?

Ти готовий рухатися далі, якщо можеш:

- запустити всі тести та пояснити, яку поведінку перевіряє кожен;
- поставити breakpoint і словами описати шлях виконання;
- виконати основні дії без миші та перевірити назви через VoiceOver;
- пояснити Debug/Release і призначення signing простими словами;
- дати іншій людині README, за яким вона зможе зібрати та запустити проєкт;
- показати чистий diff, зрозумілий коміт, скриншоти й короткий опис архітектури.

## Критерії готовності

- [ ] Тести проходять і перевіряють поведінку, а не деталі реалізації.
- [ ] Можу поставити breakpoint і пояснити шлях виконання.
- [ ] Основні дії доступні без миші.
- [ ] Відомі Debug/Release та призначення signing.
- [ ] Інша людина може зібрати та запустити проєкт за README.
- [ ] Додав скриншоти й опис архітектури до README.
